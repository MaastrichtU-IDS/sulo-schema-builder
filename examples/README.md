# Example schema artefacts

This folder holds the schema artefacts referenced in the paper's *Data Availability*
statement. Each artefact is generated by the SULO Schema Builder from a single schema model
(`schema.json`) — they are the exact outputs of the tool's export tabs and consistency check
(`packages/schema-core/src/ontologyExport.ts`'s `generateExports`/`buildMermaid`, run directly
against each `schema.json` below).

Neither example is loadable via a dedicated in-app button any more (that UI was removed —
see `frontend/src/lib/schemaTransfer.ts`'s share-string mechanism for the current way to move a
schema between instances, or paste a pre-encoded share string via the schema list page's
**Paste share string**).

## Clinical Health Record (`clinical-health-record/`)

The case-study schema: **32 classes, 41 properties**, aligned to SULO (30 classes) and SNOMED CT
(2 classes). HermiT reports it **consistent and coherent** (no unsatisfiable classes).

| File | Description |
|------|-------------|
| `schema.json` | The schema model (classes, properties, SULO mappings, mapping patterns) — the single source the artefacts below are generated from. |
| `clinical-health-record.rdfs.ttl` | Plain RDF Schema (RDFS) vocabulary. |
| `clinical-health-record.owl.ttl` | **OWL DL** ontology with SULO-compliant `owl:equivalentClass` restrictions (`owl:imports` SULO). This is the artefact the consistency check reasons over. |
| `clinical-health-record.shacl.ttl` | SHACL node shapes and property constraints. |
| `clinical-health-record.uml.mmd` | Mermaid `classDiagram` (UML) rendering. |

### Reproducing / checking

The OWL artefact can be checked for consistency with any OWL DL reasoner, e.g. via ROBOT + HermiT:

```bash
robot merge --input clinical-health-record/clinical-health-record.owl.ttl \
            --input https://w3id.org/sulo/sulo.ttl \
      reason --reasoner HermiT
```

No new experimental (patient) data were generated; these are schema artefacts only.

## OMOP CDM Schema (`omop-cdm-schema/`)

The worked modelling-error case study behind `docs/omop-consistency-issues.md` and
`docs/omop-modeling-error-examples.md`: **22 classes, 90 properties** mapped from the OMOP Common
Data Model's core clinical tables to SULO. Unlike the Clinical Health Record example, this one is
**deliberately flawed**: it is consistent as a bare TBox (no individuals, all 22 named classes
satisfiable), but a full OWL DL reasoner (HermiT) finds it **incoherent** — **44 unsatisfiable
classes**, from 25 property mappings whose SULO alignment violates SULO's relation domains/ranges
or its `∀hasPart` category restrictions. See `docs/omop-consistency-issues.md` for the full
breakdown by category and `docs/omop-modeling-error-examples.md` for the worked Turtle/OWL
derivations.

| File | Description |
|------|-------------|
| `schema.json` | The schema model — the single source the artefacts below are generated from. |
| `omop-cdm-schema.rdfs.ttl` | Plain RDF Schema (RDFS) vocabulary. |
| `omop-cdm-schema.owl.ttl` | **OWL DL** ontology with SULO-compliant `owl:equivalentClass` restrictions (`owl:imports` SULO). This is the artefact the consistency check reasons over. |
| `omop-cdm-schema.shacl.ttl` | SHACL node shapes and property constraints — these do **not** surface the incoherence above (SHACL validates asserted data, not class satisfiability). |
| `omop-cdm-schema.uml.mmd` | Mermaid `classDiagram` (UML) rendering. |

### Reproducing / checking

```bash
robot merge --input omop-cdm-schema/omop-cdm-schema.owl.ttl \
            --input https://w3id.org/sulo/sulo.ttl \
      reason --reasoner HermiT
```

Expect this to report 44 unsatisfiable classes, not a hard inconsistency — this is an
*incoherent* ontology (some classes provably empty), not one with a false statement forced by the
data (there is none: no individuals are asserted).
